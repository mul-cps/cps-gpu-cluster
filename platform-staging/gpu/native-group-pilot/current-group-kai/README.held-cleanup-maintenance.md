# One held prepared cleanup during compatible software maintenance

The default compiler path still requires every ledger claim released. The optional `held_cleanup` path is deliberately restricted to the CPS `shared-gpu-lab` five-GiB workspace, a reviewed exact member-reservation set and one retained binding, with a paired Node/Gateway image successor. It neither releases custody nor admits workloads.

`held_cleanup_maintenance.validate` is pure and performs no API, host, GPU or database operations. Its closed packet contains independently reviewed ledger/observation hashes, the prior complete released ledger, actual immutable enrollment, original raw prepared journal, full physical inventory, before/after epoch, original Pod fullspec, absence observations, complete SQL rows and both workspace inventories. The compiler also requires the independent `expected_held_cleanup_sha256` pin. Every prior ledger row must remain identical and released; precisely one additional claim must remain `releasing`. The journal is observed `prepared`, with null readback and no retirement/recovery. This does not prove a finite write never occurred: a process could have crashed between a driver write and journal readback. Fresh physical inventory is mandatory. Explicit observations must establish absence of the exact gate receipt file both before and after the host observation; prepared/null readback does not imply receipt absence. Counts are independently reviewed/pinned (current case167released predecessors, CPS8/CIT1workspaces, SQL3+1), never hardcoded in the validator. Every entry in the complete inventory must be offline, pinned and zero-charge; the original exact cgroup entry must additionally be unlimited. This deliberately strong maintenance condition fits the observed complete106-entry map. These facts do not constitute a normal retirement or cleanup receipt.

SQL reservation rows, the binding's original JSON string, ledger/journal bytes and the workspace's `stopping` state are preserved in the plan. The helper validates correspondence; it does not rewrite, normalize or save the input records. All other workspaces must remain stopped. The result explicitly reports `release_authorized: false`.

Require exact equality to the reviewed custody snapshot. A new claim, SQL drift, changed epoch, reappearing cgroup/client, altered protected Pod or stale/partial observation blocks the operation.
5. Apply only the reviewed compatible Node/Gateway cohort using the existing fullspec/data CAS machinery. Preserve held ledger/SQL/workspace state and every historical archive. ## Reviewed stage design for the current recovery cohort

This is an execution design, not an implemented actor or authorization to run it.

- **Before peer changes:** reobserve the reviewed original prepared/null-readback journal and gate-file absence on both sides of the host observation, complete inert inventory, unchanged epoch, exact held ledger/SQL/workspace rows and protected notebook facts. Establish the existing maintenance fences and matching actual backups. The independent original raw journal remains an immutable evidence artifact.
- **Stop and apply:** use the established writer/Source/peer stop order, fresh read-only SQL fences, full UID/RV/spec/data CAS and durable intent/readbacks. Retain the held claim and all three member reservations/one binding. Do not touch the claim or create a release receipt. Apply the exact compatible Node/Gateway pair; unchanged Hubs, Binder, policy, driver epoch and all unrelated settings retain their pins.
- **Resume peers and release the Node startup hold:** preserve ledger, SQL binding JSON string, member rows and workspace stopping state exactly. Once the new Node reconciles, its current journal may legitimately advance from the original prepared record to its new typed `prepared-offline-unlimited` cleanup state and publish the genuine immutable cleanup receipt. The pre-upgrade validator must not be applied blindly to that changed current journal. The actor requires the actually shipped new codec: reconstruction of the original prepared record must equal the independently pinned original; raw/canonical original hashes, terminal journal hash, enrollment UID/hash and actual immutable receipt must all validate. A different record, receipt or transition blocks maintenance. This is not permission to modify the original evidence or manually manufacture the successor.
- **Observe real component ACKs, then rotate configuration:** Node readiness can be published while the claim remains releasing: the cleanup receipt is published before the current custody verification and ACK, and the unchanged ledger/enrollment/head fingerprint still matches. Require the real upgraded Node/Gateway checks and ACKs; never synthesize them. Complete the one genuine configuration rotation with the existing writer and original anchor/archive-chain checks. - **Only after cohort readiness and completed rotation:** invoke the normal authenticated Stop reconciliation through the upgraded Gateway. Require its independent actual receipt/enrollment validation and ordinary reservation-release path. This is the sole authorized custody transition. The actor then switches from the exact held snapshot to an explicitly verified released successor: every original prior claim stays byte-identical; only the selected claim may undergo its canonical release; the normal SQL rows disappear and the workspace reaches stopped through its normal lifecycle. No actor edits these databases or the ledger.
- **Restore and audit:** verify all expected services ready at their exact specs, the real released successor, SQL0, stopped workspace, unchanged personal notebook lifetimes, unchanged original archives/anchor and restored admission/temporary permissions. An interrupted release stays held until the normal protocol succeeds; no fallback clears state.

The actor needs distinct pre-upgrade, typed-cleanup-published and genuine-released-successor validation phases. Only the first pure compiler phase exists in this change. Root must separately review the actual fresh host probes, new codec/image provenance and every stage's exact allowed transitions before any actor implementation or execution.
