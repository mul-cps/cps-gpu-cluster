# NAS Pod egress qualification

Status: controlled fixture passed; production egress/complete privacy are not qualified.

CPS and CIT singleuser NetworkPolicies were read live and cloned into a separate namespace, with no production changes. A batch fixture reproduced its current lack of egress restrictions. All three unprivileged clients could initially connect directly to the existing NAS `193.170.30.58:2049`. They mounted an operator-owned NFS qualification folder through a PVC, so native file traffic originated at the node. TCP 111 and the internal NAS address were already unreachable at baseline; those results are not evidence of a new firewall effect.

The compiler in `scripts/compute-platform/restrict-nas-egress.py` adds the central `nas-endpoints.json` host exclusions to every applicable IP allow rule, including DNS-only and unscoped rules. It preserves peer selectors, ports, existing exclusions and explicit deny-all policies. Kubernetes egress rules are additive: appending a separate restrictive policy cannot override an existing broad allow rule. The compiler emits JSON for review and performs no cluster writes. Its IPv4-only scope does not qualify future IPv6/mesh aliases.

Compiled CPS/CIT/batch fixtures all blocked the previously reachable NFS port. DNS and HTTPS remained available; each notebook client reached its matching mock Hub HTTP service, while CIT's pre-existing restriction to the other Hub mock remained intact. Every client still created, fsynced, read back and removed its own bounded file through the mounted NFS path; hashes matched. Five unit regressions cover additive public/private rules, unscoped/DNS rules, selector preservation/idempotence, existing deny-all and explicit ingress-only conversion. The actual compiled output was applied in the isolated namespace and tested, not inferred from values text.

A legacy CPS singleuser Pod still has a `dask-sa` projected token. The live `dask-admin` binding in `jupyterhub` grants Dask CR creation/patching, which can produce workers outside the singleuser selector and pass arbitrary Pod template options to the Dask operator. CIT's inspected singleuser Pod has automount disabled. No human Pod was exec'd or stopped, and no credential was exported. This legacy path must be restricted to reviewed launchers/permissions, and host-network/service-account template bypasses must be closed before activating global allowances or claiming privacy.

Production rollout must cover every user execution Pod, preserve existing restricted peers/ports, modify all intersecting broad egress allow rules, and survive Helm/Fleet reconciliation. Do not convert an ingress-only policy blindly: another selecting policy may already restrict egress, and adding a broad allow would loosen it. A restrictive namespace fallback and Dask/template admission require review together. An isolated singleuser exclusion is insufficient. Node-side NFS mounts, approved artifact relay access and real Hub/SDK traffic must pass after the complete rollout.

The central endpoint definition preserves NFS server `193.170.30.58` and adds internal address `10.71.1.55` only as a denied Pod destination; it does not change storage mounts. TrueNAS interface inventory confirmed `10.71.1.55` as its LAN address. Additional routed mesh/IPv6 aliases, off-host backup, V1 handover and cross-group file authorization remain open. Exact baseline/post-compile results and the discovered legacy permission gap are in `nas-egress-qualification-report.json`.
