# Controlled Hub registry activation

The image handover and registry configuration are separate operator phases.
Neither offline tool calls Kubernetes, migrates a database or starts a server.
New neutral accounts remain stopped and outside the qualified native GPU owner
list. Preserve the existing reviewed owner identifiers and storage paths.

## Closed image transitions

`qualified_hub_package_handover.py` accepts only these immutable pairs:

1. `c22c7460...` → `bc32b73d...` (released permanent legacy login guard).
2. `bc32b73d...` → `466b8398...` (reviewed neutral-account registry).

Both Hubs must use the same pair. Reverse, skipped, mixed, mutable and foreign
images fail. The original closed request schema, exact completed journal and
seed custody, Source revision, driver epoch, immutable projections, four actual
fresh process acknowledgments, Role UID/rules and complete Deployment/Secret
CAS protections remain required. The original pair's serialized plan remains
byte-identical to the reviewed implementation at `aab28d5`.

The first handover's running operator intent/runner is hash-bound to its original
helper. Finish its delivery activation/readback before adopting this helper for
the next transition. Never modify an in-flight runner or monkeypatch image pins.

## Separate private configuration compiler

After the exact `466b8398...` image handover is qualified, pause delivery as
required by its runbook and capture the actual current Hub Secret. Keep the
matching database archive, role/service inventory and every configuration input
private. The compiler accepts one Source at a time:

```bash
python platform-staging/gpu/native-group-pilot/hub_neutral_account_activation.py \
  --compile --input /private/source-request.json \
  --backup /private/matching-hub.pgdump \
  --output /private/new-configuration-intent
```

Without `--compile` it is inert. Request files and output use `0600`; the archive
may be `0400` or `0600`, must be an owned regular single-link file, and must not
change while hashed. The compiler streams the archive and requires its actual
SHA256 and byte count. It never defaults or fabricates a backup digest.

The closed version-1 request fields are `source`, `target_image`, `secret`,
`secret_sha256`, `neutral_owners`, `legacy_owners`, `services`, `roles`, `backup`.
Use `cps`/`jupyterhub`/`cps-admin`/`cps-admin-api` or
`cit`/`cit-jhub`/`cit-admin`/`cit-admin-api` consistently. `target_image` must be
the exact published registry image. `secret_sha256` uses the renderer's canonical
SHA256 representation of the entire actual Secret. Its UID/resourceVersion and
complete data are tested in the emitted JSON patch, together with type `Opaque`.
No other Secret data key changes.

`services` must prove the selected actual Hub Service has the selected API role;
`roles` must prove that role belongs only to that Service and retains the captured
scopes, with no user/group assignments. Use trusted actual Hub ORM/API capture,
never the console browser's OAuth roles. The private backup proof contains the
actual archive `sha256`, `bytes`, `source`, `hub_version=5.5.2`, `secret_uid` and
`values_sha256` (SHA256 of decoded `values.yaml`). The operator establishes that
this archive belongs to the matching actual Hub database/application; the
compiler verifies byte/configuration custody, not archive semantics or restore
qualification by inference. Confirm the matching PostgreSQL client/server and
archive manifest separately. CPS qualification uses PostgreSQL 15.17, CIT 18.4.

The compiler verifies the reviewed inline authentication AST and exact existing
Source owner list, then replaces only the inline class/authenticator assignment
inside `zy-native-group-access` with the released
`install_workspace_account_provisioning` helper. It retains the remaining
role-preservation and native lifecycle/Share code. It adds only
`custom:cps:provision:workspace-account` to the matching Service API role.
It replaces only the unique YAML guard scalar and preserves every byte outside
that scalar, including comments. Duplicate YAML path keys, owner/authenticator
assignments and captured role keys fail closed. It verifies that the complete
decoded target equals the intended values and preserves all other Secret fields.

Retain all reviewed existing neutral owners permanently. Temporary compatibility
owners must be an explicit sorted subset; the existing zero-scope marker user
compatibility remains on this bounded critical path. Retiring it is a separate
reviewed change. No `admin:users`, image/profile/resource override, fresh GPU
owner permission or arbitrary sharing scope is added.

Before Root applies the patch, recapture and compare actual current Secret,
Service/role inventory and the reviewed image. Previously generated byte-fixture
packets can be stale and are not deployment authorization. Apply only the exact
full-CAS patch, restart under the controlled process/permission workflow, obtain
genuine fresh four-component readback, inspect the permanent registry/schema and
confirm legacy account access/denial behavior. Then retire the explicit migration
flag through a separately reviewed configuration/readback. Keep the matching
database/configuration/application backups and original journal/PVC intact.

## Evidence and limits

The compiler and image transition have positive and adversarial offline tests.
The actual registry image executed compiled private `zy`/adoption configuration
against fresh actual Hub archives restored into isolated PostgreSQL 15.17 and
18.4. The harness supplied unchanged inherited role definitions from those
restored archives, executed Hub role initialization and handler registration,
verified only the matching Source API role gained a scope, and exercised initial
registry migration plus stopped-account creation/exact retry. PostgreSQL 18.4
also passed the noneditable actual Hub ORM registry contract suite.

These results qualify the bounded software/configuration path. They do not prove
live deployment, visitor OAuth login, fresh-workspace lifecycle/authorization,
new GPU-owner publication, cross-Hub pooling or production GPU sharing. Root
must complete those separate live acceptance gates.
